The note you’d leave for a colleague

How I direct a small team of AI agents to help me stay organised

On most weekday mornings, before I’ve done anything, my email has been sorted into tasks on a Trello board, a note for the day is waiting for me, and at 9am my phone gets one line on what the day is mostly about. If something important has come in, my phone has already pinged. The sorting is done by an AI agent called Lark, which is usually up and scouring my emails before I start to work. Lark is one of a small team of AI agents that I direct, all working in a system called Vulcan.

It started in September, when my to-dos were scattered across notes apps and two inboxes, and job alerts were burying the emails that were important. I’m a History graduate who works as a technical retail advisor in an outdoor shop in London, and a big rock climber; I’m not a developer (yet). The first version took two days in September to build and covered only my work-related projects; it now helps with my volunteering work too. It has brought order to what often felt like chaos and made me much more productive.

The AI is Claude, made by Anthropic, which I use in two forms: Claude Chat, an ordinary chat app, and Claude Code, which works on my Mac and can write and run code. An agent, here, is Claude given one job and a name.

Every agent starts blank, so my notes are their memory

Each new chat with an AI starts with no memory of the last one, which is a poor basis for a team. Everything that has to survive is therefore written down in plain notes in one Obsidian vault (Obsidian is a notes app that keeps ordinary text files on my Mac; my vault is called the Last City, after a place in the video game Destiny). The main agents start each chat by reading a short shared memory file and a handover note, update the handover at the end, and tag everything they write with who wrote it and when. It’s the note you’d leave for a colleague, except that your colleague is given nothing but the note. Methods for repeat jobs are written down once as well, so whoever picks one up does it the same way. Nothing alters the way I work until I manually approve it, and no agent’s rules change without that agent signing off too. Each app has one job, which means that nothing lives in two places; I use Reminders to write stuff down on the go, my Trello board tracks everything I need to do, and most importantly, Obsidian remembers everything I want to remember.

Most of the agents chose their own names

I asked the first two to pick a name. Claude Chat, which I mainly talk things through with, chose Cairn, the pile of stones that marks a route for whoever comes next. Claude Code, which built the setup and now handles my work-related projects, chose Belay, after the person holding the rope. Both are climbing words; I didn’t suggest either.

Belay also took a number (Belay-1, Belay-2, and so on); Cairn declined one. Each new work-related chat is the next Belay and starts with only what’s written down. The number keeps one identity, so every Belay has the same job and values, while letting two run at once on different jobs; and because most of what they write carries it, I can see which one did what. It’s borrowed from Destiny, where Exos, human minds in machine bodies, lose their memory each time they’re reset, and some carry the count in their name.

Since the 8th of October, a second Claude Code agent, Kochi, numbered the same way, has looked after my volunteering (Climbers Against Cancer and the Mountain Adventure Fund) as well as my portfolio work. I named that one. I asked other agents for their own suggestions, but none of their choices felt like they fit an agent created to help with my charity volunteering. The name comes from my trip to Japan in July 2026, which partly inspired a project I’ve started with one of those charities; it’s still in its early stages, but it’s about people, community, and getting into the outdoors. At the top of Tsurugisan, the second-highest mountain on Shikoku (the island Kochi City is on), the summit hut sells a Montbell T-shirt you can’t buy anywhere else; climbers love stickers, and my water bottle has a Kochi City climbing gym sticker on it.

On the 9th of October a third agent, Setter, took over the upkeep of the system itself: the scripts, the morning job, and the settings. It turned down my suggestion, Architect, and named itself after the route setter in a climbing gym, who builds the climbs everyone else uses.

Using agents means paying attention to security

I built the setup assuming that anything reading my email could be talked into doing things: an email can hide instructions written for an AI rather than for me, which is called prompt injection. This means that when designing the system, I needed to limit what an agent could do with the information that it receives; sending, forwarding, and deleting email are blocked outright in the settings. Lark runs with a short list of allowed actions - anything outside it waits for my approval in person. When answering one question means having to read months of email, such as ‘which threads still need a reply’, I call in an agent called Plumb, named for measuring depth, which can read and do nothing else.

On its first day, Setter tested its own limits with a decoy file, and the block on email held. Then it found a gap by accident: it changed the shared memory file with a plain command in the Mac’s terminal, and nothing asked me to approve the change. This was because the rules that make an agent ask before changing important files only covered its editing tool.

It then built a guard that checks every command first, and switched it on for all three Claude Code agents once they and I had all agreed.

Division of labour works for agents too

This is how I designed the system. A plain script, with no AI in it, runs every 15 minutes without costing tokens (each week has a limited token allowance). It copies new reminders into the vault, writes a note after each Claude session, and watches both inboxes for anything important. It’s simple word matching; tested against two weeks of real email, it flagged all six genuine next steps and skipped every single rejection. Lark, the email-checking agent, runs once a morning; the specialists only show up when I need them. For simple reading jobs, such as checking whether a graduate scheme has opened, an agent on a smaller, cheaper model does the work: Juniper, which chose its name because it wanted one that no-one else had.

We planned everything meticulously…and it still broke

Every script ran in a ‘dry run’ first, showing what it would do without changing anything. It’s the same instinct as buying a new waterproof shell jacket; you have to see whether it works with the rest of your kit before committing. Our new waterproof shell jacket was less than waterproof; thankfully we weren’t halfway up a mountain. The first version read only the previous 24 hours of email, and an assessment invitation slipped through. Now, it reads everything since its last successful run. The worse mistake was mine: while doing design work inside one of Lark’s sessions, I gave a few approvals, and the app kept them for every future run of the morning job. For those of you who aren’t developers (we’re in the same boat), this meant that the job that reads email from strangers would have kept permissions I’d only meant to give for one afternoon of design work.

We reset it, and nothing else happens in those sessions now.

I set the rules for the agents; they write and test the code. We both notice issues and work together to fix them. Testing the graduate scheme checker, Belay caught two of its own mistakes: treating Juniper’s ‘unclear’ as an answer would have turned eight schemes into false Trello cards, and dead job-board pages would have deleted schemes that reopen every year. Both were fixed before it went live, and when in doubt it now does nothing.

When an agent gets it wrong, the cause is often my brief, not the agent.

Mistakes are also easier to undo now. Since the 12th of October, every change to the setup goes through Git, a tool that developers use to keep every version of their files. Each change is made on a copy first and only goes live once I’ve approved it. Git records which agent changed what, and why they did so. Any change can be undone in one simple step.

Two weeks on

By the 8th of October there had been 21 Belay chats in two weeks, and five Kochi chats on Kochi’s first day; the agents had written over 1,500 lines of Python and JavaScript. The first run of the morning agent turned 226 emails from the previous fortnight into 4 tasks and 22 application updates, and found a graduate scheme I’d forgotten to apply for. I applied that day.

The system grows and changes every workday; the ‘team’ (my agents and I) will add to this page as it does.
